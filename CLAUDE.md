# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Nothing but Docker is installed on the host: every tool (Go, Node, wails3, golangci-lint) runs in the `develop` container, through make.

```sh
make image          # builds the development image (docker compose build develop)
make sh             # a shell in it
make test           # go test -race -cover -tags purego ./... (same as CI; go.mod ignores frontend/node_modules)
make cover          # coverage.out and the coverage of every function
make lint           # golangci-lint
make generate       # regenerates frontend/bindings from the desktop services (wails3 generate bindings)
make frontend       # npm ci && npm run build in frontend/, into frontend/dist
make frontend-test  # the frontend's lint, type check and tests
make build          # bin/tarhche for this machine, built in the container (CGO_ENABLED=0)
make build-all      # every released platform into dist/
make desktop        # make build, then ./bin/tarhche --desktop on the host
make app            # bin/Tarhche.app (and its zip) for a Mac of the host's architecture: open bin/Tarhche.app
make icons          # renders every icon from build/icon.svg (scripts/icons.sh), outputs committed
make docker         # the production image
make release-check  # goreleaser check
make snapshot       # what a release publishes but its images, into dist/, publishing nothing (needs a normal checkout: git)

docker compose run --rm develop go test -tags purego ./internal/api -run TestClientDo -v   # a single test
```

Go 1.27 (`toolchain go1.27.4`). **Every build is `CGO_ENABLED=0 -tags purego`**, and a binary is built `-tags purego,production` (`BUILD_TAGS`), which leaves Wails' dev tools out: the desktop app is Wails v3.1 with its purego backends, which load GTK4/WebKitGTK 6.0 (Linux) and AppKit/WebKit (macOS) at run time; Windows is pure Go. So one static binary per platform is cross-compiled from anywhere, and the CLI runs on a server with no GTK at all: only `--desktop` needs the libraries. Without the tag on Linux, Wails tries cgo and pkg-config. On Linux such a binary is linked to glibc's loader (purego dlopens), so the image's binary is built `-tags nodesktop` instead (`cmd/tarhche/nodesktop.go`): the CLI alone, static, on `scratch`; `make test` runs `cmd/tarhche` and `internal/upgrade` under both.

## What it is

`tarhche` is the Tarhche CLI. Run as it is, it is a command line that works as docker's does; run with `--desktop`, or started as an app is, it opens a desktop app over the same contexts and sessions. It manages everything the web dashboard manages (content, users, roles, workloads), forwards a workload's ports to the host, and copies files in and out of workloads.

- `cmd/tarhche` — `main`: `--version` and `--desktop` are acted on before the console runs; everything else is the console's. **Started as an app, it is the desktop app** (`launch.go`): with nothing to run and started by what starts apps (`terminal_*.go`): on macOS by launchd (its parent is pid 1) with no terminal on stdin, stdout or stderr, as Finder, the Dock or `open` start `Tarhche.app`; on Windows in a console of its own (`GetConsoleProcessList`), which Explorer opens for a console program and the desktop app lets go of (`FreeConsole`), a shortcut's `--desktop` too; elsewhere with no terminal at all (a desktop entry, a file manager). Where no desktop app can be opened (no display, or the `nodesktop` build: `unavailableError`), it is the CLI after all. The `rsrc_windows_*.syso` beside it give `tarhche.exe` its icon and manifest.
- `internal/command` — what every command is built on: `Cli` (streams, `Globals`, `Config()`, `Context()`, `Auth()`, `Tokens()`, `Client(ctx)`), `Exit(err)` (how errors are reported and which status a command exits with), `UsageError`/`StatusError`, the argument checks, `Alias`. `commandtest` runs a command against an API a test serves.
- `internal/command/commands` — the console: global flags and every group. `system` (login, logout, version, upgrade, info, context), `content` (a group per content resource, built from `internal/resource`), `workload` (vm, container, image, network, volume, stack, snapshot and docker's shortcuts: ps, run, rm, logs, ...), `remote` (attach, exec, cp, port-forward; registered by `workload` in the container and vm groups and at the top level).
- `internal/api` — the API client: signs requests with a `TokenSource`, renews a refused token once, `*api.Error` for what is not a success (`code`/`message` failures, `errors` validation by field), `List`/`All` for the `{items, pagination}` listings.
- `internal/auth` — signing in (browser: OAuth 2.1 authorization code + PKCE, answered on 127.0.0.1 at the port of a client registered once per context and kept in its config, registered again when the port is taken or the estate forgot it; or a password) and keeping a session fresh: renewed 30 s before its access token runs out and once a token is refused, a password session at `/api/auth/token/refresh`, an OAuth one at the token endpoint by its own client; a session that is gone signs in again in the browser by itself when the Cli is interactive. `internal/credentials` keeps sessions (keychain over go-keyring, split across entries `<context>`, `<context>:1`, ... past what Windows keeps in one; else a 0600 `credentials.json`), with doubles in `credentials/mock`; `internal/browser` opens a page; `internal/config` keeps contexts (`~/.tarhche/config.json`).
- `internal/resource` — every dashboard resource described once (routes, key, default table); the CLI's generic commands and the desktop app's generic pages are both built from it.
- `internal/workload` — a typed client of the workload's routes, both audiences, in the manifest shape (`inspect` writes what was answered, kept raw), and `NewResolver`: a VM by uuid, slug or name, a container by uuid, Docker id (or a unique prefix of 4+), or name, with its VM; `workloadtest` is a fake API with fixtures shaped like the backend's. `internal/units` reads and writes sizes (`512m`, `4g`: bytes end to end).
- `internal/stream` — the client of `docs/streams.md`: `Dialer` (ingress + token as the bearer subprotocol, a 401 renewed once, refusals as `*stream.Error`, a 403 said by its `Explainer`: `access.StreamExplainer` names the permission it needs, `access.StreamPermission` maps an action and whose the VM is to it, pings every 30 s), `Attach` (a terminal), `Exec` (the channel protocol: stdout, stderr, stdin and its end, resize, exit code), `Forward` (a `net.Conn`), `Relay` (a TCP connection through `nc` in a Docker VM), `Runner`; `streamtest` is a fake ingress speaking all three protocols. `internal/portforward` listens locally and pipes each connection to what a dial opens; `internal/transfer` is docker cp's semantics over a runner (tar in a VM, `docker cp` in a container's Docker VM), refusing archives that escape; `internal/reach` is how a workload's port is reached (a VM's published port through `forward`, else relayed by `nc` inside a Docker VM; a container's relayed to its address there) and the dialer of a context, shared by the remote commands and the desktop app.
- `internal/upgrade` — the self-upgrade, `tarhche upgrade`'s: reads the releases of `Tarhche/cli` on GitHub's API (`Check`, `Release`), and `Install`s one in place of the running binary (`Target`): the archive GoReleaser named for this platform (`tarhche_<v>_<os>_<arch>[v<arm>]`, a zip on Windows), or `tarhche_<v>_darwin_app.zip` run from a macOS app bundle, which is replaced whole; checked against `tarhche_<v>_checksums.txt`, staged beside the target and renamed over it (Windows puts the running `.exe` aside as `.old` first), nothing replaced unless all of it succeeded; extraction is bounded and nothing lands outside the bundle or goes through a link. The image's `nodesktop` build refuses (`ErrUnsupported`). `upgradetest` fakes GitHub's releases and builds their archives.
- `internal/formatter` — docker's `--format`: a table by default, `json`, or a Go template, with docker's template functions and `ago`, `bytes`, `default`.
- `internal/desktop` — the Wails app: `Run` (window, tray, a non-interactive auth manager that opens the browser through Wails), a `Workspace` holding the Cli of the context in use, and plain services bound to the frontend (Session, Resources, Workloads, Terminals, Forwards, Files; errors reach it as a `Failure`), testable without a window; `Streams` adapts `internal/stream`, `portforward`, `transfer` and `reach` to what Terminals, Forwards and Files need. `frontend/` — React 19 + TypeScript + Vite + Mantine 9 (+ xterm.js), built into `frontend/dist` (which keeps its `.gitkeep`) and embedded by `frontend/embed.go`; its bindings in `frontend/bindings` are generated (`make generate`) and committed; vitest for its tests.

## The API it talks to

A context names an estate: its API (default `https://backend.tarhche.com`) and its workload ingress (default `https://workload.tarhche.com`), which streams are opened on (`docs/streams.md`). The API answers in the language `X-Language-Code` names (`--language`; English unless told otherwise). Listings answer `{"items": [...], "pagination": {"total_pages", "current_page"}}` and take `?page=`. A refusal is `400 {"errors": {"field": "message"}}`; a workload failure is `{"code", "message"}`. Workload resources are answered in their kind's manifest shape, `{kind, metadata, spec, status}`. One's own things are under `/api/dashboard/my/...`, anybody's (what an administrator manages) under `/api/dashboard/...`.

## Conventions

- **A command is a type of its own, in a file of its own named after what it does** (`list.go`: `type listCommand struct`, `newListCommand(cli)`), implementing `console.Command`. `Configure` keeps the flag set and defines the flags with `console.Var`; `Run` is `return c.cli.Exit(c.run(ctx))`, and `run` checks its arguments first (`command.ExactArgs(c.flags, 1)`). Flags come before arguments: the console stops at the first argument. Output goes to `cli.Out` through `internal/formatter`, errors are returned, never printed by the command, and nothing is logged.
- Docker's names and flags wherever docker has the command: `ls` (with `ps` and `list` registered as `Alias`es where docker has them), `rm`, `inspect`, `-q/--quiet`, `-f/--force`, `--format`, `-a/--all`. One's own things are listed by default; `--all-users` (`-A`) lists anybody's, through the administrator's routes.
- Tests: one `Test<Unit>` per unit, `t.Parallel()` first, its cases as `t.Run` subtests, also `t.Parallel()`; testify's `assert`/`require`; an API is an `httptest` server (`commandtest.New`). Test doubles live in a `mock` package beside what they stand in for. Every package's logic is covered.
- Doc comments on every exported (and most unexported) type and function; no inline comments narrating what a block does: rename instead.
- The desktop frontend uses `@mantine/core` components directly, no wrappers of its own for what Mantine ships; one layout adapts to every width. To look at it without a window, build `-tags purego,server` and Wails serves it over HTTP (`WAILS_SERVER_PORT`; it answers only the Host it binds), which a headless browser can drive.
- **Permissions are the estate's to decide, and a hint here.** A command is always offered; when the API refuses it (403), `access.Explainer` (wired into every client `Cli.Client` builds) says why: a blocked account (even `/api/dashboard/profile` is refused), a permission the token's `permissions` claim lacks (named, from `access`'s table of what each API route is asked under, kept in step with the API by hand), or a role disallowing it on that one resource. A stream the node refuses is named the same way (`access.StreamPermission`, `stream.WithExplainer(access.NewStreamExplainer(audience))`): attach, exec and forward, each `self.workload.vms.<action>` on one's own VM and `workload.vms.<action>` on anybody's (`-A`). The desktop app offers only what the claim allows (`Session.Permissions`, re-read every minute and on focus without asking the API; `Resources.Definitions` flags; `Workloads.Abilities`), and goes back to its login when a session ended (`auth.ErrSessionEnded`) or the account is blocked or refused (`access.ErrBlocked`, `auth.ErrAccountRefused`).
- The repository is public: test fixtures name made-up people, never anybody real.
- **Icons are rendered, never drawn by hand**: `build/icon.svg` and `build/icon-dark.svg` are the Tarhche logo (the frontend repository's `public/icon.svg` and `icon-dark.svg`); `make icons` (`scripts/icons.sh`, librsvg and ImageMagick in the develop image) renders the app's icon (`build/appicon.png`, the logo on a white rounded square on macOS's icon grid), the window's and the Dock's (`internal/desktop/icons/app.png`), the tray's glyphs, the bundle's `build/darwin/icons.icns`, `build/windows/icon.ico`, the Linux entry's `build/linux/tarhche.png` and the `.syso` resources, all committed.
- **What a release ships beside the archives**: GoReleaser's universal-binary hook runs `scripts/app.sh`, which wraps the universal binary in `Tarhche.app` (`build/darwin/Info.plist`, its version from the tag) and zips it as `tarhche_<version>_darwin_app.zip`, published and checksummed with the rest; a Linux archive holds `build/linux/tarhche.*`, the desktop entry (which runs `tarhche --desktop`) and its icon. The app is not signed beyond the linker's ad-hoc signature, nor notarized.
